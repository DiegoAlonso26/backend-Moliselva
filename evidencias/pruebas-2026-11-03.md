## Hallazgo H-01 resuelto: respuesta incompleta al rechazar JWT

Los cinco casos de `rechazaTokenInvalidoConErrorJson` fallaron inicialmente:

- Firma incorrecta.
- Token vencido, fuera del margen de tolerancia.
- Usuario indicado por `uid` inexistente.
- Usuario inactivo.
- `sub` diferente al usuario del `uid`.

**Esperado:** HTTP 401, tipo de contenido JSON y cuerpo
`{"codigo":"NO_AUTENTICADO","mensaje":"Token ausente o inválido"}`.

**Observado antes de corregir:** HTTP 401 con cuerpo vacío, sin `Content-Type` y con encabezado
`WWW-Authenticate: Bearer`. La petición sin token sí devuelve el JSON esperado.
La identidad inválida queda bloqueada; la diferencia es el contrato del error.

Las 40 combinaciones de ruta y rol pasan con su estado HTTP esperado. Los
rechazos por permisos devuelven el JSON `SIN_PERMISO`; el login es accesible sin
`Authorization`. Los JWT de prueba se firman realmente y el rol efectivo se
consulta en el repositorio simulado, incluso cuando el token anuncia otro rol.

La configuración inicial definía un manejador general de autenticación, pero no
uno explícito en el servidor de recursos OAuth2, que devolvía la respuesta
Bearer predeterminada. El primer PR conservó ese hallazgo siguiendo la regla 0.1
de la guía. Después, Diego autorizó expresamente modificar producción y fusionar
el PR una vez resuelto.

**Corrección:** `SecurityConfig` comparte los manejadores JSON de autenticación
y permisos entre la configuración general y el servidor de recursos OAuth2.
Los cinco casos ahora devuelven HTTP 401 con el JSON esperado, y la matriz de
permisos sigue pasando. Las pruebas originales se mantuvieron sin cambios.
